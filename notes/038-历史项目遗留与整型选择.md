# 038 · 维护旧项目：什么时候保留 int，什么时候需要固定位宽

OpenSSL 的同一个函数里，`uint32_t` 用来存数组元素，`uint64_t` 用来容纳较宽的中间结果，`int i, j` 只用作循环下标。维护时先看每个变量需要表示的范围，以及谁会读取它。项目年代不能替这些声明给出理由。[OpenSSL 32 位 Curve448 实现](https://github.com/openssl/openssl/blob/openssl-3.2.0/crypto/ec/curve448/arch_32/f_impl32.c#L24-L38)

## 遇到 u8、u32，先追到定义

Linux 读取 gzip 头时，用 `const u8 *buf` 指向字节，用 `size_t size` 表示缓冲区长度。代码要逐字节比对 `1f 8b 08`，所以一个数组元素正好对应一个文件字节。若要查 `u8` 的来源，在该版本头文件中搜索 `typedef __u8`，可找到 `typedef __u8 u8;`。同一内核的调试模块则用普通 `int` 保存异常嵌套层数 `exception_level`。[Linux gzip 头读取](https://github.com/torvalds/linux/blob/v6.7/kernel/module/decompress.c#L59-L69) · [Linux 整数别名](https://github.com/torvalds/linux/blob/v6.7/include/asm-generic/int-ll64.h#L16-L23) · [调试模块声明](https://github.com/torvalds/linux/blob/v6.7/kernel/debug/debug_core.c#L73-L89)

OpenSSL 旧版 `aes_local.h` 的 `typedef uint64_t u64;` 可以直接读作“给 `uint64_t` 起名 `u64`”。同文件的 `u32` 却要多查一步：构建时定义了 `AES_LONG` 就是 `unsigned long`，否则是 `unsigned int`。复看录屏应打开旧版文件。2026-11-20 核实，OpenSSL 主分支已在 2026-05-27 删除这里的四个短别名，相关宏改用标准定宽类型。[旧版头文件](https://github.com/openssl/openssl/blob/openssl-3.2.0/crypto/aes/aes_local.h#L27-L34) · [OpenSSL 上游变更](https://github.com/openssl/openssl/commit/1e6dbc7340a8c406c32f6713768de363bdadfdf8)

## 改类型之前，先看它用在哪里

如果还要支持旧工具链，先用该工具链编译包含 `<stdint.h>` 和所需类型声明的最小程序。`int32_t` 到 C99 才标准化，且目标实现须有符合条件的精确 32 位类型才会提供这个名字。[C99 定宽整数定义](https://www.open-std.org/jtc1/sc22/wg14/www/docs/n1256.pdf#page=268)

| 场合 | 判断和做法 |
| --- | --- |
| 函数内部的计数或下标 | 值域能由 `int` 完整表示、外部也没有位宽要求，就可以保留 `int`。若改动理由是性能，应比较目标设备上同一负载的实测结果。课堂没有做性能测试。 |
| 已发布的库函数接收 `int` | 保留头文件约定的参数类型。若调用方现在持有有符号的 `int64_t v`，先用 `<limits.h>` 的 `INT_MIN`、`INT_MAX` 检查原值。范围内才转成 `int` 调用，超出时报告范围错误或改用支持更宽参数的接口。 |
| 写入文件或网络报文 | 先按格式规范确定字段占几个字节，以及高低字节的顺序。C 结构体还可能因内存对齐插入填充，仅把成员改成定宽类型，不能保证结构体可以原样写出。[Linux 结构布局示例](https://docs.kernel.org/driver-api/ioctl.html#structure-layout) |

用课堂的 gzip 格式举一个复习例子：文件头的修改时间 `MTIME` 占 4 字节，低位字节在前。值为 258（`0x00000102`）时，文件中应依次出现 `02 01 00 00`。声明 `uint32_t` 可以满足内存中的位宽要求；检查写出的四个字节，才能同时验证文件的字节序。[gzip 格式规范 §2.1、§2.3](https://datatracker.ietf.org/doc/html/rfc1952#section-2.1)
